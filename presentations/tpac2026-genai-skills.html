Tip 1

Give it more context than you think it needs

Instead of

make some test cases for aria-foo

Try

I’m a member of the ARIA WG, and I need to develop some test cases for aria-foo for this task issue <GitHub issue link>. We’re in my local copy of the WPT repository; existing accessibility tests include those in /accname, /wai-aria, /html-aam and more. There is a sibling repo at ../wpt-metadata with an identical hierarchy and META.yml files listing keywords/labels, including “accessibility”. Search that repo to understand which tests already cover accessibility. Note that aria-foo only became testable recently with WPT extensions including getAccessibilityProperties (see an example test in ./wai-aria/pressed) and the aamtests in ./core-aam/aamtests/. Read the GitHub issue, local docs and related tests. Start in planning mode before making any changes.

Worked example · wpt-metadata#9537

Accessibility tests that wpt.fyi couldn’t find

Many accessibility tests had no accessibility/a11y label in wpt-metadata, so they didn’t show up under label:accessibility on wpt.fyi.

  • Detect

    Find tests using get_computed_role / get_computed_label, ARIA test helpers, or ARIA/role file names

  • Label

    Whole directory where the suite is all accessibility; single files everywhere else

  • Follow convention

    Match how dpub-aam/ is already labelled; skip manual tests, which produce no CI results

Tip 2 · What went wrong

It also labelled conformance-checkers/, and CI caught it

  1. 1 · Agent

    Adds labels to three conformance-checkers/ folders

  2. 2 · CI

    Path validation fails: those are support files for an external validator, not tests wpt.fyi runs

  3. 3 · Fix

    A second commit drops those labels; the PR merges

Check the output against something real: CI, the linter, wpt.fyi. “Looks right” isn’t a check.

Tip 3

When a task will come back, turn it into a skill

  • SKILL.md

    The judgment: what counts as an accessibility test, the labelling conventions, the exceptions (manual tests, conformance-checkers/)

  • script.py

    The mechanics: the repeatable search, so the agent doesn’t rediscover it (and spend tokens) every time

Labels drift as new tests land. Next time, anyone can rerun it. Where should it live? interop-accessibility#256

Second example · ARIA PR review skill

Reviewing a w3c/aria PR the way an editor would

  1. 1 · Gather

    Script pulls the PR, diff, linked issues, every suite spec and the WPT index

  2. 2 · Classify

    Editorial or normative? Affects authors, user agents or AT?

  3. 3 · Style

    ARIA and W3C style guides, on changed lines only

  4. 4 · Cross-spec

    Search every suite spec and ARIA in HTML for contradictions and needed follow-ups

  5. 5 · Tests

    Find existing WPT and validator tests; draft missing ones as .tentative

  6. 6 · Process

    Labels, ACT, APG, MDN, browser bugs, consensus, review count

Design choices worth copying

  • A verdict and blocking issues first

  • Paste-ready GitHub review comments

It says what it checked vs inferred

  • Plan before changing

    Knowledge in reference files, mechanics in scripts

  • You own what you submit

    The agent drafts; you review and sign off

Slide 12 of 13

You own what you submit

One way to do it: the draft PR loop

  1. 1 · Draft

    The agent files a draft PR against the ARIA or WPT issue

  2. 2 · Self-review

    You review the diff on GitHub; the agent adds follow-up commits from your review

  3. 3 · Ready

    Only you move it from Draft to Ready for review

  4. 4 · Human review

    Other reviewers, often starting with their own agentic first pass

It depends on your workflow. Where GitHub and AI tools are built into the IDE (Xcode, Visual Studio), the loop may look different.
